## 本次对话形成的实现

### 计数主链路

- 覆盖用户关注数、粉丝数、获赞数、获收藏数、作品数，以及笔记点赞数、收藏数。评论相关业务不在此次改造范围。
- 关系、作品发布及删除使用业务事实与 Outbox 同事务；计数服务消费关系与作品事件。
- 点赞、收藏入口等待 Broker 确认后返回已受理，事实在笔记服务的顺序批量消费中处理。已受理不代表业务执行成功。
- 互动事实与不可变的命令处理结果同事务提交；事务外调用计数 RPC；所有目标成功后才确认原消息，不再发送第二层计数 MQ。
- 计数按目标分组，由 Lua 执行事件去重、增量聚合和写回。用户为 40 字节 String、笔记为 16 字节 String；每个字段使用 i64 存储，运算限制在 Lua 可精确表达的整数范围。
- 每个目标单独维护 seen Set。跨目标部分成功后可整批重试，成功目标跳过已处理事件。
- 删除作品与互动操作使用作品行锁；删除事件携带数据库互动快照。内部允许负值抵消迟到增量，查询展示时才截断为零。
- 笔记详情、搜索展示及索引重建通过计数 RPC 查询。搜索热度排序仍依赖索引快照，不宣称实时排序。

### 查询竞态修复

## 审查结论与待实现设计

正常业务处理、重复消费及跨目标部分失败的重试链路基本成立；不能将其表述为已经完成 Redis 数据丢失恢复或生产级可靠性验证。

确认存在的限制：seen 按事件持续增长；Redis data 与 seen 一起丢失时不能仅凭缺失判断是否为新目标；当前没有可执行的快照重建和去重回收流程。

不采用“给 data、seen 同时加 TTL”的做法。删除去重记录可能导致旧事件重复累加，删除 data 则丢失历史累计值；MQ 保留时间也不能代表全部业务重放边界。

已写入文档但尚未编码的恢复方案：

1. 暂停相关业务写入与事实消费、计数写入，等待在途事实事务和计数调用结束。
2. 从稳定业务事实计算完整快照，写入独立的新计数代次。
3. 事实事务保存 `countGeneration`；Outbox 和互动结果重试保留原代次。计数侧跳过已经包含在快照中的旧代次增量。
4. 重建前已入 MQ 但未执行事实的互动命令，恢复后在新代次执行，不能按入队时间丢弃。
5. 各库代次切换完成后恢复业务，再回收封存代次的 Redis 数据与 seen。跨库切换失败时保持暂停，按同一 rebuildId 继续，不宣称分布式原子提交。
6. 互动结果与 Outbox 不因 Redis seen 回收而自动删除。若一直不执行重建，当前代次 seen 仍会增长。

当前代码未新增上述代次字段、控制表、重建任务、暂停边界或清理任务，也未修改 Redis TTL。后续编码前需先阅读开发文档第 4.8 节，不能把文档方案当作已完成能力。

## 追加记录：受控计数恢复与删除缓存修复（2026-10-29）

### 本次目标与开发规则

修复两个问题：Redis 丢失已确认计数后缺少可执行恢复入口；删除笔记在数据库提交前失效缓存，可能回填旧状态。
继续按实习简历项目标准，保留原模块结构并复用已有代码，优先清晰命名、普通循环和方法注释。本轮未提交或推送 Git，未执行数据库迁移，也未修改实际 Redis 服务端配置。

### 受控计数恢复实现

- 在原 `xiaohashu-data-align` 模块新增 `CountRebuildXxlJob`，XXL-JOB 名称为 `countRebuildJobHandler`。参数为唯一 `rebuildId`，只手动触发，不设置周期重建。
- 新增迁移脚本 `xiaohashu-data-align/src/main/resources/db/count-recovery.sql`：创建 `t_count_generation`、`t_count_rebuild`，为互动结果表增加 `count_generation`。ALTER 属于一次性迁移，不能重复无条件执行。
- 关系事件、作品事件、互动处理结果和内部计数变更 DTO 携带代次。事实事务记录代次；互动结果重试复用原代次；未执行的互动命令在实际处理时取得当前代次。
- 计数侧跳过旧代次事件，拒绝缺失或未来代次请求，只更新当前代次。历史 Outbox JSON 的缺失代次固定解释为第一代，不能解释为运行时当前代次。
- 第一代沿用原 Redis 键名，后续代次采用 `counter:gN:{user:ID}:data/seen` 与笔记对应键。新快照按绝对值覆盖，重试不累加。
- 关注数、粉丝数都从有效 `t_following` 统计；作者作品数及获赞、获收藏仅包含有效作品；笔记内部点赞、收藏保留已删除笔记的有效互动口径。按 ID 分批遍历目标，显式写入零值。
- 准备阶段先提交 `REBUILDING` 状态；加载失败保持暂停，必须用同一个 `rebuildId` 重试。完整快照加载成功后才切换代次并标记 `COMPLETED`。已完成任务重复触发直接返回。
- 新增共用工具 `CountGenerationUtils`，在事实事务和计数请求中读取代次并持有共享行锁；重建任务用排他锁等待在途操作结束。相关读写在恢复期间等待或失败，不能读取半成品。

**与原第 4.8 节跨库设计的区别：**本轮核对当前本地配置后，按关系、笔记、计数、数据对齐共用一个 MySQL 事实库实现，使用一张共享代次表。尚未实现多库协调切换。每批计数读写增加一次 MySQL 代次查询，这是为降低恢复实现复杂度作出的性能取舍，不能描述为计数查询完全不访问 MySQL。

**尚未实现的能力：**自动回收旧代次、在线无停顿对齐、多库恢复协调、自动发现 Redis 全量丢失。当前代次 data、seen 仍无 TTL；旧代次暂保留，不能宣称去重存储已有固定上限。

### 删除笔记缓存修复

- `NoteServiceImpl.deleteNote()` 不再在事务内直接删除 Redis 详情缓存或发送本地缓存失效广播。
- 复用 `NoteCountEventService` 和原 `t_note_event_outbox`，新增 `CACHE_INVALIDATE` 任务，与删除事实同事务提交。
- `NoteOutboxPublisher` 仅能领取已提交任务。先删除 Redis 详情缓存，再发送本地缓存失效 MQ，全部成功后才标记任务完成；失败保留原任务重试。
- 业务回滚时失效任务一同回滚；重复执行删除缓存和失效广播是安全的。
- 本轮解决提交前失效窗口，不宣称解决所有慢查询并发回填问题，也未重新设计其他笔记操作消息链路。

### AOF 与部署说明

新增 `docs/count-recovery.adoc`，记录配置、升级及手动恢复流程：

- 实际 Redis 服务端需配置 `appendonly yes`、`appendfsync everysec`；data 与 seen 同受持久化保护。everysec 仍有丢失窗口，不能代替事实重建。
- 计数键不设 TTL，不能参与业务缓存淘汰。推荐独立计数实例使用 `noeviction`；共享实例时需评估对全部缓存键的影响。
- 升级前停止旧版服务并执行一次性 SQL，再统一部署新版，禁止旧版实例或直接 SQL 绕过恢复屏障继续修改事实。
- 重建前关闭业务写入口及其他直接修改事实的任务；完成后检查 READY、COMPLETED，再开放业务。
- 本轮仅完成代码、SQL 和操作说明，未对运行环境启用 AOF，未执行真实恢复任务。
