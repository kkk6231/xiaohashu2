= 点赞收藏链路说明

== 当前实现

* 入口用 Bloom、最近 100 条 ZSet、pending 和必要的 MySQL 查询判断状态；通过后更新缓存，发送 `NoteInteractionEventV2`。
* 服务端生成 `eventId`；事实消费组 `note-interaction-facts-v2` 顺序写 `t_note_like` / `t_note_collection`，计数消费组 `counter-note-interaction-v2` 按目标和 `eventId` 在 Redis 去重后更新计数。
* 两个消费组均从最早可用位点开始；已有消费位点不受影响。
* 永久非法消息记录日志后跳过；数据库异常交给 MQ 重试。
* Broker 明确拒绝时按缓存版本条件失效；超时或其他结果未知时保留缓存，接口返回 `UNKNOWN`。
* Redis 更新和 MQ 发送不构成事务；少量互动可能不落库，事实和计数允许短暂/少量不一致。
* 不再使用互动结果表、`count_status` 补偿任务和非法消息隔离表；笔记发布及删除的生命周期 Outbox 保留。
* 计数 Hash 丢失但去重集合存在时读取返回 `null`，写入失败并重试或进入死信，需要人工处理；不支持自动恢复。

== 已接受的边界

* Redis 成功而 MQ 未发送：允许少量互动最终没有落库。
* 事实和计数由两个消费组独立处理：计数允许少量偏差。
* `eventId` 只处理同一 MQ 消息的重复投递；用户重新发起请求会生成新 `eventId`。
* 列表、事实、计数由不同环节更新，允许短暂不一致；计数 `+1/-1` 到达顺序可以不同。
* 最近列表只缓存 100 条；缓存未覆盖的分页回查 MySQL。
* 删除/改私密与互动并发时可能留下事实表记录，列表查询会过滤不可见笔记。

== 旧方案

旧版使用 `NoteInteractionCommandV1`、`requestId`、`t_note_interaction_result`、`count_status`、补偿任务和计数 RPC，已经移除，不再作为当前实现。
